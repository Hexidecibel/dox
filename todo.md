## Found while building — 2026-09-03

- **`/review` is reachable by URL for a role the nav hides it from.** Three layers disagree: nav gates `/review` to admins, the route in `src/App.tsx` is UNGATED, and `/api/queue` allows `user`. So a `user` works the review queue by typing the URL. Conversely `/spec-alerts` is shown in the nav to `user` and the route bounces them to the dashboard. `/import` and `/orders` have the same ungated-route shape. No data leaks (the API gates independently) but the UI gate does not hold. FIXED BY the one-surface-table work in the approved wizard plan — do not patch separately or there will be a fourth opinion.
- **Nothing links a document to a requirement automatically.** `functions/lib/kinds/coa.ts` writes zero `document_requirements` rows; `syncDocumentFacets` is only reachable from `documents/[id].ts` and `ingest.ts` and both need the CALLER to supply requirement ids. There is no `document_type_requirements` table. An approved COA closes nothing unless a human ticks boxes by hand — the gap engine has been running on data nothing produces. Covered by the approved plan (`functions/lib/requirement-defaults.ts`).
- **`shared/renewalPeriod.ts` anchors renewal periods on `primary_metadata.$.effective_date`, and nothing ever extracts `effective_date`** — not a canonical field, not an alias, not named in any prompt. Period-based renewal proposals are therefore silently unavailable on every AI-extracted document; only a human typing the date can feed them. Needs its own measured change: on a certificate of insurance, "Effective Date" is a decoy for `document_expires_on`.
- **`bin/clone-org` loses all registry and spec config.** It copies documents and suppliers but none of `requirements`, `claim_types`, `claim_type_requirements`, `supplier_requirements`, `spec_tests`, `spec_limits`, `owner_routes`, `document_type_extraction_instructions`. A clone arrives looking configured and empty underneath — worse than starting fresh. Covered by the approved plan.
- **Certificate of Analysis has no type-level extraction instructions.** `bin/seed-doctype-extraction-instructions` covers ten types and the most common one is not among them.
- **`/api/graphql` bypasses `functions/api/_middleware.ts` entirely** — it is in `PUBLIC_ROUTES` and authenticates itself in `functions/lib/graphql/context.ts`. Any middleware-based gate has a hole there.
- **The extraction router does not self-heal.** After the Tailscale outage both machines were reachable and serving Q8, but the router kept advertising a stale model list until `qwen-llm.service` was restarted by hand. Needs a keepalive and an alert when a model chain resolves empty.

- **`/api/graphql` module gating — DONE, and the original claim here was overstated.** CORRECTION: this note previously said a client could query orders / records / expirations data through graphql with those modules off. That was wrong, inferred from the endpoint bypassing `_middleware.ts` rather than from reading the schema. `functions/lib/graphql/schema.ts` exposes only tenant, users, user, documents, document, lookupDocument, searchDocuments and auditLog — **zero** references to orders, records, lots, expirations or spec checks. The real divergence was ONE resolver: `generateReport`, the twin of `POST /api/reports/generate`, which `/api/reports` already assigns to `fulfillment` — so the same report was a 403 over REST and a 200 over graphql. Now gated, with both transports emitting identical denials from `denialForModule`. Every resolver file exports a module map, so a NEW resolver with no entry fails to compile.
