- **`/api/graphql` module gating — DONE, and the original claim here was overstated.** CORRECTION: this note previously said a client could query orders / records / expirations data through graphql with those modules off. That was wrong, inferred from the endpoint bypassing `_middleware.ts` rather than from reading the schema. `functions/lib/graphql/schema.ts` exposes only tenant, users, user, documents, document, lookupDocument, searchDocuments and auditLog — **zero** references to orders, records, lots, expirations or spec checks. The real divergence was ONE resolver: `generateReport`, the twin of `POST /api/reports/generate`, which `/api/reports` already assigns to `fulfillment` — so the same report was a 403 over REST and a 200 over graphql. Now gated, with both transports emitting identical denials from `denialForModule`. Every resolver file exports a module map, so a NEW resolver with no entry fails to compile.
- **Every permission error on graphql is masked to "Unexpected error."** Pre-existing and verified empirically: a `reader` calling `users` gets `{"message":"Unexpected error.","extensions":{"code":"INTERNAL_SERVER_ERROR"}}`. `createYoga` masks anything that is not a `GraphQLError`, so `ForbiddenError` / `NotFoundError` / `BadRequestError` / `UnauthorizedError` all lose their message and their status. The graphql API is materially less debuggable than REST, and this is why the module gate had to throw a real `GraphQLError` to survive. Worth fixing, but it touches the permission boundary so it wants its own deliberate pass.
