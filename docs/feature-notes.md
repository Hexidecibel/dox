# Feature notes

The full design notes for each dox feature, moved VERBATIM out of `CLAUDE.md` (which now carries a
one-to-two-line summary per feature under `## Key Features`). Each `###` heading below is the bold
feature name used in `CLAUDE.md`, so `grep -n "Feature Name" docs/feature-notes.md` finds it. The
bullet under each heading is the original text, unedited. **Read the entry before changing that
feature, and update it here (not in `CLAUDE.md`) when the feature changes.** Per-migration rationale
is in `docs/migration-history.md`.

### API Keys

- **API Keys**: Programmatic access via `X-API-Key` header (`dox_sk_` prefix). Created/revoked by admins. Keys auth as the creating user.

### Document Ingestion

- **Document Ingestion**: `POST /api/documents/ingest` — upsert by `external_ref` + `tenant_id`. Creates new doc or adds version. Designed for agentic/email pipelines. Supports `source_metadata` (JSON).

### Document Lookup

- **Document Lookup**: `GET /api/documents/lookup?external_ref=X&tenant_id=Y` — find document by external reference.

### Password Management

- **Password Management**: Forgot password (self-service email flow), admin reset (generates temp password, sets `force_password_change`), force change on next login.

### Document Preview

- **Document Preview**: Inline preview for PDF (iframe), images (img tag), text/CSV (rendered inline). Office docs show download card.

### File Name Search

- **File Name Search**: `GET /api/documents/search` now also matches against `file_name` in document_versions (joined).

### Products

- **Products**: Global product catalog shared across tenants. Tenant-product associations track which suppliers provide which products.

### Document Types

- **Document Types**: Per-tenant document type definitions (COA, Spec Sheet, SDS, etc.) replacing freeform categories.

### Document-Type Classification (its own pass, before extraction)

- **Document-Type Classification (its own pass, before extraction)**: `classifyDocumentType` in `functions/lib/llm.ts` (mirrored in `bin/process-worker`) reads the first 3000 characters against the tenant's **own** `document_types` catalog and picks one name **verbatim**, or answers `none`. It runs BEFORE extraction, on the `fast` chain, so the 0098 document-type instruction layer — which is keyed on the type — applies to the first and only full extraction instead of needing a re-extract. The answer is validated by EXACT (normalized) name/slug match only: a near miss is left unresolved and recorded in `processing_queue.document_type_guess` for a human, never fuzzed onto the nearest type, because a confident wrong type silently selects the wrong instruction block forever. A type an intake door already declared is trusted and never re-classified. Measured on `tests/fixtures/doctype-corpus`: 19/40 → 38/40, ~2.6 s per document. On **real** supplier documents (`tests/fixtures/real-corpus`, `bin/eval-aj-docs`) it holds at 27/31 — and, importantly, **15 of the 18 documents whose correct answer is "none" get it**, which is the behaviour the exact-match rule exists for: 17 of one packet's 26 parts have no matching type in the FSQA starter pack at all, and being parked for a human is right.

### Real-document regression corpus

- **Real-document regression corpus**: `tests/fixtures/real-corpus` + `bin/eval-aj-docs` (`--verify` needs no model; `--classify-only`; `--force-ocr`; `--rescore`). The three synthetic corpora each assume one file is one document, of a type in the catalog, with a text layer; a supplier packet breaks all three at once. **The PDFs are tracked here** — a real PDF has no `html/` source to rebuild from. One standing finding lives in it: a 36-page / 25-document packet is classified ONCE (it answers "Letter of Guarantee" and takes page 3's expiry for all 25). The second — **an inserted certificate image never reached OCR** — was FIXED on 2026-09-17 by per-page OCR routing (below), taking the corpus from 70.4% to 89.6% value accuracy; `--verify` now checks the OCR ground truth on the production route, so it is the no-model regression test for that rule.

### Shelf life and document number (the two fields the corpus proved had no slot)

- **Shelf life and document number (the two fields the corpus proved had no slot)**: measured, not guessed — `bin/eval-aj-docs` scored `shelf_life` as MISSED on all four real specification sheets and `document_number` on both Country Morning sheets, because neither was a canonical field in rule 1. Both are now canonical in **all three mirrored prompt copies** (`functions/lib/llm.ts` BASE_PROMPT + the text and VLM prompts in `bin/process-worker`), pinned byte-identical by `tests/unit/shelfLifeAndDocumentNumberFields.test.ts`. **`shelf_life` is ONE VERBATIM STRING** including the storage condition ("21 days at <=40F", "1 year frozen, 21 days refrigerated"): a parsed `{days, basis, condition}` has to invent something the moment a page states two lives for two conditions, so the page's own words are the answer and a multi-condition statement is never flattened. **It is the PRODUCT's life and is NOT an input to `shared/renewalPeriod.ts`** — the sharper form of the mistake 0097 exists to prevent, since this one is already a PERIOD and the ladder's tiers 5-7 are periods; "21 days" would propose re-collecting a spec sheet three weeks after it was issued, when a spec sheet renews at three years by TYPE (`tests/unit/shelfLifeNotRenewal.test.ts`). **`document_number` is the paper's own identifier** — not a lot, PO, order, item, customer item, plant or revision number, never a footer FILE PATH, and **never on a certificate** (there its number is `certificate_number`, including when the page labels that line "Document #" — both IFANCA halal certificates do, and the first draft of the field pulled it out of `certificate_number` and backfilled that from a per-product table column). The guidance is in the BASE prompt and NOT the 0098 type layer, deliberately: the type layer only applies once a type resolves on an exact match, and on the real corpus 13 of 30 documents resolve at all — a field defined only there is undefined on exactly the documents nobody has configured. Measured on `tests/fixtures/real-corpus`: value accuracy **89.4% -> 96.5%**, all four shelf lives and both document numbers landing, the previously-graded fields unchanged-to-better (101/107 -> 103/107) with their one fabrication gone; `tests/fixtures/doctype-corpus` 7 of 7 new rows correct. Shelf life also answers a live client question — the SME was asked to supply per-product shelf life by hand while the sheets already state it.

### The model chain going empty

- **The model chain going empty**: `bin/check-model-chain` asks the router and exits non-zero naming the models a chain needs. A degraded chain passes (a working chain is a working chain); an unreachable router passes (`models.js` attempts the chain anyway — this must not be stricter than the code it guards). `bin/eval-aj-docs` runs it first and exits 3 rather than scoring a half-finished corpus. `bin/process-worker` preflights **`fast`** alongside `best`/`vision` and **warns without aborting**: classification runs on `fast` and fails non-critically, so a `fast`-only outage otherwise produces no error anywhere while every document extracts untyped and the 0098 layer applies to nothing.

### Per-Page OCR Routing (the page that is a picture with a caption on it)

- **Per-Page OCR Routing (the page that is a picture with a caption on it)**: every OCR decision used to be asked of the WHOLE file — is the text layer empty (`bin/process-worker`), is it garbled (`isTextGarbled`), is it >200 characters with no letters (`shared/pdfTextSerializer`'s guard)? A page that is a **pasted certificate IMAGE with a typed caption, a confidentiality banner and a page number over it** answers "no" to all three, so tesseract never ran on it. On the client's own 36-page packet that is pages 6 and 13-16 — the SQF certificate, two OU kosher letters, two IFANCA halal certificates, 4 to 81 characters each over a full-page image — and **they are the only five documents in the file that carry expiry dates**. They scored 0 of 25 graded fields and were 25 of the corpus's 34 value errors; this is also the likeliest reason `document_expires_on` had never been populated once across 601 prod documents. **The rule is a PAIR and both halves are required**: one drawn image covering **>=25%** of the page AND a text layer under **300 characters**. The same packet contains a counter-example to each half alone — page 36 is a near-blank back cover (5 chars, no picture) that must not become an OCR bill, and the Smith Brothers spec sheet is drawn on a background image covering 100% of the page while carrying 1957 characters of real text that must never be replaced by a worse read of the same words. Both thresholds sit inside measured holes (coverage 0.124 -> 0.348, characters 81 -> 396), the same discipline as `SERIALIZED_MIN_LETTERS`. **OCR NEVER OVERWRITES**: a page with no usable text takes the OCR read, a page with a caption keeps the caption FIRST and has OCR appended only when it adds >=200 letters and >=3x what the page had, and a rich text layer is never swapped out. **Only the qualifying pages are rasterised** (`pdftoppm -f N -l N`), budgeted at 25 pages per document with the shortfall recorded, never silent. The rule is pure (`shared/pdfPageOcr.ts`), the Node half is one module (`bin/lib/pdfPageOcr.js`) shared by BOTH `bin/process-worker` PDF branches and `bin/lib/corpusText.js`, so the measurement harness cannot measure a text path the product does not have. A document that already went to OCR whole is skipped. Provenance is per page (`processing_queue.text_page_sources`, migration 0117) and the Review Queue's "Extracted text" panel says which pages came from an image. Measured on `tests/fixtures/real-corpus`: value accuracy **70.4% -> 89.6%**, the five image documents **0/25 -> 22/25**, `document_expires_on` now landing on all four certificates that print one; doctype corpus text byte-identical on all 40 fixtures.

### One File Is Not One Document (packet detection, migrations 0118/0119)

- **One File Is Not One Document (packet detection, migrations 0118/0119)**: a supplier's annual packet is 36 pages holding **25 separately-dated documents**, and dox treated it as one -- one classification ("Letter of Guarantee", page 3 answering for all 25) and one renewal date (`document_expires_on = 2027-01-02`, **printed nowhere in the file**: page 3's "valid one year from the date hereof" clause applied to a packet containing an SQF certificate that lapses 2026-04-23 and a kosher letter that lapses 2026-06-30). **NOTHING AUTO-SPLITS, and that is the whole design**: a wrong split turns one wrong document into twenty-five. `shared/packetDetect.ts` is pure and runs on the per-page text and per-page image coverage `shared/pdfPageOcr.ts` has already computed, so detection costs no second read of the file. Signals in order of trust: the file's **own index page** (the supplier's declaration of its structure, used VERBATIM -- the layout signals move the CONFIDENCE, never the ranges); a **repeated closing block** (the sign-off that ends every statement -- which is why running-header furniture is stripped from the page HEAD only, since a whole-page repeat rule deletes exactly this evidence); a **title-shaped opening line** against a CLOSED list of document words, so an eight-page HACCP plan's table headers cannot fire it; a **picture page**; a date line and a text-density jump, corroborating only. **When the layout signals disagree the proposal goes COARSE and says so** -- multi-signal boundaries only, low band -- rather than inventing precise-looking ones. Declines on a non-PDF, under 4 pages, or a file the COA path already split per lot (`produceCoaRecords` knows the lots). The Review Queue card (`src/components/PacketSplitCard.tsx`) sits ABOVE the extracted fields, because on a packet every field below it is one contained document's answer wearing the whole file's name: **Split into N documents** / **Adjust** (merge, move a boundary, drop a part) / **Not a packet** (remembered). On confirm, `functions/lib/packet-split.ts` carves every range with the splitter that already exists (`kinds/coaPageScope.ts#extractRecordPdf`) BEFORE writing any row, then makes one child queue item per part at `processing_status='queued'` with the type NOT inherited (inheriting it is the original defect in a hat) and the supplier inherited (the one fact a packet genuinely answers); the parent keeps its file as the source of record and the approve path refuses it. Measured with `bin/packet-detect` (no model calls): **26/26 ranges exact** against the parts recorded in `tests/fixtures/real-corpus/corpus.json`, page 36 reported as covered by no part rather than bolted onto the last document, and **zero false alarms** over 4 real spec sheets, 40 doctype fixtures and the packet's own 8-page HACCP master plan. The cheap half is 0119: a request-composer line can say **"one document per file"** as a flag rather than as prose, rendered on the supplier portal.

### Expired on Arrival (rules table G4, migration 0121)

- **Expired on Arrival (rules table G4, migration 0121)**: a certificate whose approved `document_expires_on` is before the day it ARRIVED (`documents.arrived_at`, stamped at approval from the queue item's `created_at`; falls back to `created_at` and says so) is flagged on the Review Queue card, does NOT close its requirement in the gap engine or the request composer's closure read (it stays open with `gap_reason: 'expired_on_arrival'`, the document listed under `not_counted`), and on approval writes a `document.expired_on_arrival` audit row and notifies the "QA" owner route through `resolveAlertRouting` with `adminFallback: false` — unrouted is the renewal-style routing gap (audit row + notice to org_admins saying nobody was alerted). Pure rule `shared/expiredOnArrival.ts`; D1 half `functions/lib/expired-on-arrival.ts`. Nothing is held.

### Fixed-Window Renewal (rules table G3, migration 0125)

- **Fixed-Window Renewal (rules table G3, migration 0125)**: a document TYPE can renew inside a calendar window on a fixed cycle instead of N months from issue. `document_types.renewal_window` (JSON `{opens, closes, every_years, reference_year, source}`) REFINES the `period` policy (months = every_years x 12, read only under `period`, cleared when the policy leaves it) -- not a fourth policy word, because widening 0097's CHECK means rebuilding a table six others CASCADE from. `resolveRenewalExpiry` tier 3b (`rule: 'document_type_window'`): due at the CLOSE of the first window that OPENS strictly after the effective date, ABOVE the printed expiry per the ruling ("goes stale at the close of the window whatever date the document prints"); no effective date = `unresolvable`, said in words; a period set on the document itself still wins. `FDA_FOOD_FACILITY_REGISTRATION_WINDOW` (21 CFR 1.230(b): Oct 1 - Dec 31 of even years) is the starting value for a type NAMED like an FDA registration via `defaultRenewalSettingForTypeName` (API create, both pack appliers, `bin/fix-starter-pack-renewal-policy`), visible and editable on Document Types ("Fixed calendar window"); AJ's table marks those dates pending his verification. Frozen into `renewal_snapshot` as `type_renewal_window`.

### Packet Provenance (rules table H1, migration 0126)

- **Packet Provenance (rules table H1, migration 0126)**: an approved packet PART cites the packet it came from: `document_versions.source_packet_queue_id` + frozen `source_packet` (`PacketCitation`: file name, day received, checksum, page count, page range, part n of N, the index's label, who split it), written by `functions/lib/packet-provenance.ts` after ANY approve path, current version only, never rewritten (`document.packet_source_recorded`). A part's `documents.arrived_at` is the PACKET's arrival, not the split day (G4). Rejecting the split container keeps its file with NO reclaim date. `GET /api/documents/:id/download?source=packet` returns the original packet (document access rule, audited `document_packet_source_downloaded`); Version History says "Split from packet ... pages a-b, part n of N -- open the original packet".

### Sales Sheet Check (rules table F6)

- **Sales Sheet Check (rules table F6)**: `shared/salesSheetCheck.ts` flags a queue item filed as a specification sheet (type, or the guess when untyped) that carries NO controlled-document mark (extracted revision/effective/issue date; printed revision/issue/effective/next-review date, "Supersedes", "Approved by", a document number, "Page x of y"); marketing copy only sharpens the wording. Silent on all 7 real + synthetic spec sheets, fires on the arrivals-demo sales sheet. Queue GET attaches `sales_sheet_warning`; the card's "Reject as sales sheet" opens the reject dialog with the preset `sales_sheet` reason chosen. Warn, never block.

### Requirement Scope (migration 0123)

- **Requirement Scope (migration 0123)**: a requirement is owed once per supplier (default), per PRODUCT, or per LOT (`requirements.scope`, vocabulary `shared/requirementScope.ts`). A per-product requirement attached to a supplier is owed by every ACTIVE product of it -- linked through `product_suppliers` OR the legacy `products.supplier_id` (every reader ORs both), `products.active = 1`, not marked no longer supplied -- minus `product_requirements` exemptions (reason required) plus its `add` rows. **A pair closes only through a confirmed document linked to that product** (`document_products`); a confirmed document linked to no product closes NOTHING and is listed as `unattributed`, never read as "every product". Zero active products is open (`gap_reason: no_products`). Inactive / no-longer-supplied products and certificate-created products with no confirmed identifier (`product_suppliers.source = 'certificate'`) become caveats, never silent. **Gated amber**: only a supplier with a per-product requirement (or an add row) has its products judged; there a product with nothing applying and no "nothing owed" declaration is `not_configured` and the supplier reads `products_not_configured` (precedence not_configured > open > products_not_configured > satisfied) -- a supplier-scope-only tenant is byte-identical apart from `products` (golden-pinned in `tests/unit/requirementScopeGap.test.ts`). Claims: a `document_claims.subject_type = 'product'` claim opens a per-product requirement for that product only; facility claims apply supplier-wide with a caveat. 'lot' is stored but judged once per supplier with `lot_scope_not_evaluated` (per-lot checking is a later phase). Loader `functions/lib/requirement-gaps.ts` (`loadGapInputs`, `loadConfirmedClosures` -- the one closure read, also used by the request composer so a per-product ask is never shown closed by an unattributed document). API: scope on `/api/requirements` (audited `requirement.scope_changed`) + read-only `GET /api/requirements/:id/scope-preview`, `/api/product-requirements`, `PUT /api/suppliers/:id/products/:productId` (no longer supplied / nothing owed). UI: gap panel per-product grid + unattributed list, Supplier › Products Requirements column + `ProductRequirementsPanel`, Settings › Requirements "Owed" select with impact preview. Existing tenants: `bin/propose-requirement-scopes --tenant <id>` (dry run default; `--apply`; `--remote --apply` prompts). Product-level analyte panels (Phase 2) and per-lot checking (Phase 3) are NOT built.

### Exact-Duplicate Intake + "You Already Have This" (migrations 0108, 0132)

- **Exact-Duplicate Intake + "You Already Have This" (migrations 0108, 0132)**: a file we already hold is raised at import and **a PERSON decides** (owner decision 2026-09-30; 0108 used to suppress it before any reviewer saw it). Byte-identical detection (SHA-256, same tenant) lives once in `functions/lib/intake/duplicates.ts` and runs inside `enqueueDocument`, so smart upload, both email webhooks (the legacy one calls `admitIntake` directly, before any model runs), connector drop/run/retry, the S3 poller and the supplier portal all share it. Precedence: **identical to a file still WAITING** -> no second card, an `intake_duplicates` row against that queue item, whose card says "also received from ..." (checked FIRST since 0132, so repeat arrivals follow the one card that will decide them); **identical to an approved DOCUMENT** -> QUEUED, with a ledger row (`match_kind` `already_approved`, `match_basis` `identical_bytes`, `disposition` `queued`, `queue_id` = the card) and an `intake.duplicate_queued` audit row; an approved ORDER/SHIPMENT file (records, no document to version) is still suppressed as in 0108; **identical to a REJECTED file** -> queued normally, card says "this exact file was rejected on ... for ..." (`intake_history.previously_rejected`). **The second match is the same document in a newer revision**, knowable only after extraction: same supplier (`processing_queue.supplier_id`) + same document type + the same `document_number`, or the same `certificate_number`, or -- for a lot-scoped type (renewal policy `none` or a COA name) -- EXACTLY the same lot set (a records COA is compared as the set of documents one approval produced), with DIFFERENT bytes. Exact identity keys only (numbers normalize like search keys: case/space/punctuation fold, leading zeros stay, fewer than 3 characters ignored), never a title; pure rule `shared/duplicateProposal.ts`. **Both are computed at READ, never stored**: `functions/lib/intake/already-have.ts` (`loadAlreadyHave` for the queue pages, `alreadyHaveFor` for one item) attaches `intake_history.already_have` (`DuplicateProposal`: basis + plain-words reason, the document title/supplier/approved date, `current_version` / `next_version`, and every document the matched approval produced with its lot keys) from the item's STORED extraction, so the card and the approve gate cannot disagree, and a proposal vanishes by itself if the document is deleted. **The card** (`src/components/DuplicateDecisionCard.tsx`, above the fields) says "You already have this: <title>, <supplier>, approved <date>" with a link and WHY it matched, and offers three buttons in order: **Replace existing (becomes vN+1)** -- primary, the default, helper "v1-vN stay in version history" -- **Keep as a new document**, **Discard**. The Import page shows the same card right after upload (`already_have` on the process response): Replace / Keep carry the choice to the Review Queue card (the extraction is still confirmed there), Discard acts at once. **The approve gate**: `PUT /api/queue/:id` recomputes the proposal and REFUSES an approval without `duplicate_decision` (400, `code: duplicate_decision_required`, nothing written -- nothing is decided by omission). `replace` writes the approval as the NEXT VERSION of the matched document through `writeReplacementVersion` in `kinds/coa.ts` (version row first under the UNIQUE(document_id, version_number) guard, then the document guarded on the version read; earlier versions and their R2 objects untouched; the document takes the new extraction; renewal columns become THIS paper's answer, all-NULL when nobody answered, the previous ones kept in the `document.version_replaced` audit row); products, lots, requirement suggestions, classification and the spec register (at the new `version_number`) follow the normal approve path. A records COA pairs each approved record to the matched document carrying its lot, exactly (`pairRecordsToDocuments`) or not at all; replace is refused with held records or a multi-product approval (several documents cannot be one version). `keep_both` approves as a new document. `discard` (with either status) closes the card as a REJECTION with reason `duplicate_discarded` (a `REJECTION_REASONS` value the reject dialog does not offer), so the file follows the normal 90-day rejected-file retention and the document on file is untouched. Every decision -- including a plain reject of a matched card (`rejected`) -- is written to the ledger row (`decision`, `decided_by/_at`, `decision_document_id`, `decision_version_number`; a newer-revision match gets its row at decision time) and audited `queue_item.duplicate_decided` with the same plain-words summary the toast shows ("now v3; v1-v2 stay in version history"). Portal: the supplier's response is unchanged; an arrival identical to an approved document is queued like any other (`request_uploads.queue_id`) and linked to whatever document the decision produced or versioned; a waiting twin still points `queue_id` at the waiting item. The document page's "Received again" lists every later copy with what happened to it. 0108 rows stay as history (no backfill into the queue), and **Review anyway** (`POST /api/intake-duplicates/:id/review`, Review Queue > Received again) still replays a suppressed arrival and audits. `POST /api/documents/ingest` is deliberately NOT checked -- it is a caller-asserted upsert, not a queue door. Tests: `tests/api/intake-duplicates.test.ts`, `tests/api/duplicate-decisions.test.ts`. Existing surplus copies: `bin/audit-duplicate-documents [--remote]` reports groups (first vs later copy, with every link hanging off each) and changes nothing; `bin/archive-duplicate-documents` (dry run default; `--tenant <id> --remote --apply` prompts) ARCHIVES a later copy (status only, nothing deleted) only when everything on it is already on the kept copy by CONTENT (confirmed requirement links/claims, lots, products, spec results + verdicts + acknowledgements, spec gaps, renewal decision) or is a re-pointable ledger row / pending suggestion, and SKIPS with the reason any copy an order line, accepted suggestion, bundle, supplier arrival, accepted request line, live alert/export link or note points at. One `document.archived_as_duplicate` audit row per copy names the kept copy (`bin/lib/duplicateArchivePlan.js`).

### Scheduled Renewal Alerts (per-owner)

- **Scheduled Renewal Alerts (per-owner)**: Renewal is the frequent use case, so it does not wait for a human to press a button. The `dox-renewal-alerts` companion Worker (`workers/renewal-alerts/`, deploy with `bin/deploy-renewal-alerts`) fires `POST /api/expirations/run-scheduled` daily at 13:00 UTC — Pages cannot host a cron, same reason `dox-connector-poller` exists. Alerts are **grouped by the record's owner**: `documents.owner` resolves through `owner_routes` (migration 0091, managed via `/api/owner-routes`) and each owner gets a digest of only their records, with a token-gated `/alert/<token>` link that needs no login. The routing ladder is `functions/lib/alert-routing.ts` and is shared with the spec path. **The two paths differ by one deliberate flag**: spec alerts pass `adminFallback: true` (a one-shot food-safety event should reach someone), renewals pass `false` (a recurring job that falls back to the admin pool trains everyone to ignore it). **A record with no resolvable owner is never silently re-broadcast** — it produces a routing-gap notice, an `expirations.routing_gap` audit row, and an `unrouted` block in the API response. Re-alert suppression (`renewal_alert_state`): first sight, escalation, or a 7-day cooldown. Engine: `functions/lib/renewal-alerts.ts`, shared verbatim with the manual `POST /api/expirations/notify` button. **Lead time is per document (migration 0111)**: a record is alerting when `days_until <= ` its resolved lead time, the document type's `renewal_alert_lead_days`, else the tenant's, else 60 (`resolveRenewalAlertLead` in `shared/renewalLeadTime.ts`; SME ruling 2026-09-14: some clients want 3 months to chase suppliers, others 1 month to avoid spamming them). There is no run-wide window: neither endpoint accepts `window_days` (sent anyway, it is ignored and reported as `window_days_ignored`), because the Renewals dashboard look-ahead is a VIEW filter and must never decide who is mailed. The dashboard defaults its look-ahead to the tenant lead time, and every row carries `alert_lead_days` / `alert_lead_source` / `alert_status` (digest rows and the email say "warned 90 days ahead (document type)"). **A lead-time change never burst re-sends**: the ledger is keyed on the document and knows nothing about lead times, a lead time moves a record only between `current` and `expiring` (so no false escalation), lengthening it makes never-alerted records a first send and leaves anything mailed inside 7 days suppressed, and shortening it only removes records. Set on Settings › Owner Routing ("When owners are warned", `/api/expirations/lead-time`, audited) and per type on Document Types. Both show a read-only preview first (`/api/expirations/lead-time/preview`: newly entering, would send, leaving).

### Renewal Periods + the Approval-Time Decision

- **Renewal Periods + the Approval-Time Decision**: WHEN a document is next due, resolved in exactly one place — `resolveRenewalExpiry` in `shared/renewalPeriod.ts`. The SME's rules (AJ Conner, 2026-09-02) are regulatory definitions, not preferences: annual by default (~90% of a supplier file), three years for a specification sheet (both major food-safety schemes define a current spec sheet that way), and everything else one year *or whatever the document itself states*. **`document_expires_on` is that last clause, and it is NOT `expiration_date`** — the latter is the PRODUCT's shelf life (139 of 200 prod documents carry one and all 139 are COAs, so reading it as a renewal date would have mailed every COA owner about a certificate that does not renew). Extraction asks for `document_expires_on` only on types where a document genuinely expires — insurance, certifications, audit certificates — and the prompt (three mirrored copies: `functions/lib/llm.ts` BASE_PROMPT plus the text and VLM prompts in `bin/process-worker`) forbids copying a COA's shelf life into it. **A COA resolves to `no_renewal_period` as a property of its TYPE**, not a string match at read time: `document_types.renewal_policy` (migration 0097). **Approval is where it is settled** — `resolveRenewalExpiry` is a PROPOSAL shown pre-filled and editable in the Review Queue with its `rule` in plain words, and what the reviewer confirms is written to the document with a frozen `renewal_snapshot` (`functions/lib/renewal-proposal.ts`), the same discipline as `limit_snapshot`. A cleared field means "does not renew" and is distinguishable from nobody having looked; every decision writes a `document.renewal_decided` audit row. **An `unresolvable` proposal is NOT an answer** — that rule means a period applies but there is no effective date to count from, so the box is empty because WE could not fill it; the Review Queue then sends no `renewal` key at all unless the reviewer touches the box (`src/lib/renewalAnswer.ts`), because a recorded decision with no date is read by tier 2, forever, as "a reviewer confirmed this does not renew". A deliberate empty answer under that rule is stored as `cleared`, never `accepted`. **The starting policy of a TYPE comes from one helper**, `defaultRenewalSettingForTypeName` (shared/renewalPeriod.ts), called by `POST /api/document-types` AND by both starter-pack appliers (`functions/lib/starter-packs.ts`, `bin/lib/starter-packs.mjs` via the generated `bin/lib/shared/renewalPeriod.js` mirror). The pack used to name neither column, so a tenant seeded after the 0096/0097 backfills got every type on `inherit` — including a COA proposed an annual renewal. Existing tenants: `bin/fix-starter-pack-renewal-policy` (dry run default, `--tenant`, `--remote`, `--apply`) corrects only rows still holding BOTH migration defaults with no audit row naming a renewal key, and never re-decides a setting somebody wrote.

### Documents out of Search (migration 0115)

- **Documents out of Search (migration 0115)**: the client's day is answering document requests (AJ Conner, 2026-09-14: one to three hours of it, usually forwarding to a salesperson), and search used to end at a list. Results are now SELECTABLE and leave as a ZIP or an email. **A covering result gets a checkbox; a likely / nearby one needs an explicit "Include anyway"** -- v2.11-2.13 spent real effort making "covers what you asked" and "nearby and does not" two different statements, and a checkbox on every row would quietly undo it. **One zipper, not two**: `functions/lib/document-export.ts` is the bundle download's fflate assembly lifted out, and every archive carries a `manifest.csv` naming, per file, the document, supplier, type, lot and production date (a lot date the portal itself flags ambiguous or in conflict is NOT printed as fact). The cap is STATED, not silent: over 40 MB or 50 documents is refused with the number in the message, never truncated into something that looks complete. `POST /api/document-exports/zip` writes ONE audit row naming every document -- the "every export is provable" claim the help text has been making and the /reports CSV button never honoured. `POST /api/document-exports/send` mails a **token-gated link, never attachments**, from the portal's own sender with a **reply-to of the person who pressed send** (`on_behalf_of` is free text printed as context -- nothing impersonates a recipient's domain), rate limited 30/hour per user, and the link is REVOKED if the send fails so there is never a live link nobody was told about. The recipient's page is `/export/:token` over an allow-list projection (`buildExportLandingView`, the `buildAlertLandingView` mould) holding no internal id. Module-gated under `library` (`/api/document-exports`; the public recipient routes reach the gate with no user and are never narrowed by the sender's settings). **Reader may ZIP, not send** -- downloading is the same bar as one document at a time, but minting an unauthenticated URL to fifty documents and mailing it outside the organization is publishing, so `/send` requires `user`+. **And what left can be pulled back (migration 0116)**: Documents › Sent documents (`/documents/sent`, `GET /api/document-exports/links`) lists every send -- when, by whom, on whose behalf, to which addresses, how many documents, the open/download counts and a resolved `active`/`expired`/`revoked` state (revoked wins over expired: the question is whether a PERSON stopped it). An admin sees the organization's sends, everybody else their own, and the response reports the scope it ACTUALLY answered in. **The token is never returned** -- an accountability screen that handed out the credential would be the largest hole in the feature. `POST /api/document-exports/links/:id/revoke` is immediate on all three recipient routes because all three resolve through the one gate `loadUsableExportLink`; the sender or an admin may press it, another tenant's link is a 404 not a 403, a second press does not move the first timestamp, and `document_export.revoked` records the recipients, the id list and the counts at that moment. **There is deliberately no Extend**: lengthening a link after the fact changes the terms of a mail already sent and hides it in a row nobody re-reads -- a new send is the honest answer. **One kind of link does not expire (migration 0134)**: a customer's certificate too large to attach to an order send leaves as a link minted with `neverExpires` (`document_export_links.never_expires = 1`; `expires_at` is NOT NULL and holds a far-future placeholder, the flag is the authority). `exportLinkState` reads it `active` until somebody revokes it, `loadUsableExportLink` checks revocation FIRST and always, the list and the recipient page say "does not expire" instead of printing a date, and it is revoked from this same screen like any other. It is not an Extend: the terms are set when the link is made and said in the email that carries it. The R2 read is `readExportBytes`, shared with the order send so "the file was not in storage" is decided in one place. Revoking cannot recall a file already downloaded, and the screen says so; the open counts count REQUESTS against the link, never people, because the URL is a bearer credential that travels, and the page says that in words beside the numbers.

### Manual COA Fulfillment: an order a person builds and sends (migration 0134)

- **Manual COA Fulfillment: an order a person builds and sends (migration 0134)**: the basic tier has no WMS feed, so a PERSON does what the matcher does on the automatic tier (AJ Conner, 2026-10-05/06, decisions D-040..D-051): names the customer, the customer's PO / order number and the ship date, puts the approved certificate on each product and lot, reviews it, and sends it. **ONE ORDER RECORD FOR BOTH TIERS**: nothing here is a second "manual order" object -- it is an `orders` row with `created_by` set and lines whose `picked_by` says a person filled them. `POST /api/orders` takes `ship_date`, checks `customer_id` belongs to the organization (it was stored unchecked) and answers 409 on a duplicate order number (it fell through to the UNIQUE constraint as a 500); `DELETE /api/orders/:id` clears the lines' suggestion rows first (they reference the lines with no ON DELETE action, so an order whose lines were ever matched or picked could not be deleted). **A PICK IS A PERSON'S ACCEPTED MATCH** (`functions/lib/order-items.ts`; `POST /api/orders/:id/items` with `document_ids` and/or one typed `item`, `PUT` / `DELETE /api/orders/:id/items/:itemId`, role `user`+, staged orders refused with 409, another organization's order is a 404): it writes EXACTLY the columns `POST /api/lot-matches/:id` writes on accept (`coa_document_id`, `lot_id`, `lot_matched = 1`, `coa_match_status = 'matched'`, `coa_matched_at`) plus an `accepted` `lot_match_suggestions` row with `match_basis = 'manual_pick'` (a pending engine suggestion for the same pair keeps the engine's basis -- the person accepted that evidence), so the fulfillment report reads the line `ok`, lot counts count it, and search coverage reads it as person-accepted rather than legacy. **The matcher never argues with it**: `recordSuggestion` already leaves an accepted or rejected pair alone and never re-suggests the document a line carries; taking a certificate off a line marks the pair REJECTED (not deleted) for the same reason a rejected suggestion is kept -- it cannot be offered back. `bin/audit-asserted-lot-matches` skips a hand pick because it has an accepted row. **Approved documents only**: an active document of the order's own organization with a file behind it; another tenant's, an archived or a deleted one is REPORTED in `refused` with its reason and the rest of the selection still lands (one bad id in twelve must not lose eleven, and must not be silent). **Nothing asks what TYPE the document is** -- a later "document orders for sales" feature puts non-COA documents on the same order, which is also why the send tables are named for documents, not certificates. **One line per lot row** of the picked document (a certificate for three lots is three lines); an existing line for that lot with no certificate is FILLED, not duplicated (the connector-fed order whose lines arrived bare); a document with no lot row becomes one line with no lot, which the report correctly reads `missing_lot`. A hand-typed line with a lot number resolves the lot and asks the matcher exactly as the connector does -- whatever it finds arrives as SUGGESTIONS. **Each line shows product, lot and production date so a wrong pick is visible before it goes**, and the date is shown WITH ITS DOUBT: `describeLotDate` (`shared/orderSend.ts`) turns `lots.production_date_status` / `_source` into `production_date_state` (`stated` / `decoded` / `legacy` / `ambiguous` / `conflict` / `unparseable` / `none`), a label and a note, resolved on the server so the order page and the review dialog cannot word it differently; only a `stated` date is printed plainly, and no production date is printed in the customer's email at all. **The customer gets an exact copy of each certificate ATTACHED, not the 30-day link** (`functions/lib/order-send.ts`; `GET /api/orders/:id/send-preview`, `POST /api/orders/:id/send`, `POST /api/orders/:id/sends/:sendId/resend`): from `viaSenderName(tenant)` ("<Organization> via SupDox") with a reply-to of the person who pressed send, any role except `reader` (AJ: "any user sends"), recipient = `customers.email` (one address per customer to start) and editable on the review screen, 30 sends an hour per user, 503 without `RESEND_API_KEY`. **GENERATED FILE NAMES ONLY** (H4): `exportFileNames` -- the search export's own namer, not a second one -- and the uploaded name appears nowhere in the email, pinned by a test that greps the wire. **ONE PLAN, TWO READERS**: `planOrderSend` alone decides which files go, under which names, in which email; the preview prints it and the send executes it and REFUSES (409) a plan whose `fingerprint` changed since it was reviewed. **Too big for one email is split, shown and recorded** (`packOrderSendFiles`, pure): 15 MB of files per email (about 20 MB encoded; the provider's ceiling is 40 MB and a Function has 128 MB), NEXT-FIT so files stay in line order and "2 of N" follows "1 of N"; the review screen shows the split before sending; more than 10 emails is refused with both numbers (413), never truncated; a single file over 15 MB leaves as a LINK in the first email -- `document_export_links.never_expires = 1`, honoured by `exportLinkState` / `loadUsableExportLink`, still revocable (`expires_at` is NOT NULL and holds a far-future placeholder; the flag is the authority). **One part in memory at a time**: each email's bytes are read, encoded, sent and released before the next. **A failed part is not a failed send**: every email succeeds or fails on its own, a file missing from storage or no longer the bytes that were recorded FAILS ITS PART with the reason (nothing is sent short), the send is `partial` until every part went, the order moves to `delivered` only then -- and only when no line was left behind (a line with no document, or an archived one, was listed as not sent, and an order with one of those is not delivered however well the rest went) -- the response is 200 whenever something went and 502 only when nothing did, and resend rebuilds exactly the failed emails FROM THE STORED RECORD (same files, names, subject, recipients, reply-to of the original sender) rather than re-planning. The record is written BEFORE the first email at `failed` with every file unsent, so a Function that dies half way under-claims and can never say something left that did not. **The whole certificate (rules table H2)**: a multi-lot certificate goes WHOLE, once, however many lines were cut from it. `functions/lib/coa-original.ts` walks a page-scoped document (`extended_metadata.page_scoped`) back to the Review Queue item's original: version 1 through `origin_queue_id` / the queue id in `external_ref` (they must agree); **version 2+ through the `document.version_replaced` audit row for exactly that version** -- a "Replace existing" approval writes a new version from a DIFFERENT queue item while `origin_queue_id` and `external_ref` still name the first, so those two are deliberately not read there. It never guesses: the candidate must be the same organization's, carry the file name the version was written under, and be in storage; anything less is `missing` with one of three stated reasons, the per-lot page is sent, and the review screen says so. An original over 15 MB also falls back to the per-lot page (an export link serves documents, not originals), said in words. **Retention**: the records approve path (`functions/lib/kinds/coa.ts`) no longer stamps `file_retain_until = now + 90 days` on the source bundle; it keeps it with NO reclaim date, the split-packet container's rule (H1), because a certificate a customer may ask for again next year cannot carry one. Nothing has ever purged on that column, so no original was lost to the old stamp; `bin/retain-split-originals` (dry run default; `--tenant <id> --apply`; `--remote --apply` prompts; never touches a rejected item's tombstone) reports how many source certificates are kept per organization and clears existing stamps, leaving a `queue_item.split_original_retention_cleared` audit row -- "kept" is read from the record, not from storage, and the report says so. **What left is on record**: `order_sends` (who, to whom, subject and message as sent, per-part outcomes) + `order_send_files` (generated name, bytes, checksum, part, `delivery` attachment / link, `source` document / original, every document the one file stands for); `order_id` is a bare pointer with the order number copied beside it so the record outlives the order. Shown on the order ("Sent") and on Documents > Sent documents beside link sends (`order_sends` on `GET /api/document-exports/links`, same scope rule) -- with no revoke and no open count, and the page says why: an attachment is in the recipient's inbox. Audit: `order_item.coa_picked` / `.coa_removed` / `.added` / `.updated` / `.removed`, `order.coas_sent` / `order.coas_send_failed`. UI: Orders > New Order (customer picked from those on file or typed, order number, PO, ship date), the order page's lines / Add COAs (the search workspace in a dialog: `SearchWorkspace` `selectionAction` + `globalShortcuts={false}`, with the Include-anyway gate unchanged) / Review and send / Sent, and **Add to order** from Documents. NOT built: a customer contacts screen (several recipients per customer), a customer-create permission for non-admins, per-tenant sending domains, document orders for sales. Known edge left alone: a connector that re-ingests an order number a person built DELETEs that order's lines (`functions/lib/kinds/order.ts`), which today fails on the suggestion rows' foreign key and is reported as an order upsert error -- the picks survive, by an accident worth making deliberate.

### Declared Lot Formats (Any-Field COA Retrieval, Phase 4, migration 0110)

- **Declared Lot Formats (Any-Field COA Retrieval, Phase 4, migration 0110)**: each supplier's lot format is DECLARED data (`supplier_lot_schemes`, append-only versions), never a global regex — AJ §6: "a pattern that silently mis-parses another supplier's lot is worse than no parser". A spec (`shared/lotScheme.ts`, pure, bundled for bin/) names segments with kinds and widths (`digits`/`letters`/`alnum`/`yy`/`julian_day`/`mmddyy`/`yymmdd`), an optional sublot, the identity rule (`base_plus_sublot`, or `segments` — CMF's product suffix is the item, not the lot) and WHICH date the code encodes (`production` or `best_by`). `validateLotSchemeSpec` refuses a declaration that cannot mean one thing (unknown settings, a Julian day with no year, a date with no role). `decodeLot` reads every lot shape (`1042620303`, `10426203-03`, `10426203 03`, base + sublot) and never throws: a lot that does not fit comes back `fits: false` with the reason. Declared: Darigold plant(3)·YY·Julian day + 2-digit sublot (production), Country Morning best-by MMDDYY + suffix, Andersen `none` (a declaration, distinct from no row). With no declaration the 0075 `suppliers.lot_scheme` enum is mapped onto an equivalent spec (`legacyLotSchemeSpec`), byte-identical keys, pinned against the old transform. **A decode is a validator and a labelled fallback, never an authority**: (1) Review Queue invariants `lot_fits_declared_format`, `lot_code_production_date`, `lot_code_best_by_date` flag with both values and rewrite nothing (queue reads select the current declaration via `LOT_SCHEME_SELECT`); (2) the lot writer (`productionDateFromLot` + `productionDateSets`) fills `lots.production_date` from the code ONLY when nothing is stated, as `production_date_source = 'lot_decode'` with `production_date_scheme_id`; a stated date is never overwritten, and decode ≠ stated is `conflict` with both in raw; (3) search reads a decoded date as `likely` ("Lot code implies production Jul 31, 2026 … decoded from the lot code using Darigold, Inc.'s declared format"), never covering, and a search naming a supplier with a declared production-role format plus a production date also judges that supplier's lots decoding to the day (the date constraint's `note` gives the lot shape, e.g. `???26212`). Composite identity uses the declared widths on the certificate, order and shipment sides (order/shipment through the line's product's single supplier, declared formats only). The extraction prompts no longer convert Julian codes (all mirrored copies, pinned by `tests/unit/lotCodeNotDecodedByModel.test.ts`). Admin: Supplier › Lot format (`/api/suppliers/:id/lot-scheme`, org_admin/super_admin, audited `supplier.lot_scheme_declared`) — templates, segment editor, live tester, read-only fit preview. Seed: `bin/seed-supplier-lot-schemes` (dry run default, never overwrites a declaration). Stored keys a format would store differently: `bin/report-lot-key-scheme` (dry run default; `--tenant <id> --apply` re-keys in place or MERGES into the lot already holding the identity after moving every document/order/suggestion pointer, refuses a merge whose rows state different production dates, never touches `does_not_fit`; audited `lot.identity_repaired` / `lot.merged_on_identity_repair`). Shelf life (R4) is NOT here.

### Spec Limits + Out-of-Parameter Warnings

- **Spec Limits + Out-of-Parameter Warnings**: Acceptance limits on COA test results (`spec_tests` + `spec_limits`, migration 0084). Two sources judge every result — the COA's own printed spec/pass-fail (no configuration, works on every supplier) and OUR configured limit, which is often tighter than what the supplier certifies against. **Three-state by design**: `in_spec` / `out_of_spec` / `not_checked`, where `not_checked` means we held a limit and could not honestly apply it (a censored `<50` against a ≤10 limit, a CFU/mL result against a CFU/g limit) and is never a silent pass. Engine is `shared/specCheck.ts` (pure); review-queue surfacing via `functions/lib/spec-warnings.ts`; register + alerts via `functions/lib/spec-register.ts` (one email per document; routing now delegates to the shared ladder in `functions/lib/alert-routing.ts` — owner route, then `assignments`, then org_admins, with the admin fallback passed in explicitly as `adminFallback: true` because a one-shot safety event reaching nobody is worse than a redundant email). Warns, never blocks. **Notify-only could-not-check (rules table E1/E2)**: a `not_checked` verdict may carry `not_checked_category` — `method_mismatch` (MPN against CFU) or `sample_basis_mismatch` (a presence/absence test on a smaller sample than the limit's, e.g. an absence limit configured "per 25 g") — and ONLY those join the one-per-document spec alert, as their own "not judged — please resolve with the supplier's lab" list (`isNotifyOnlyVerdict`); the category is frozen into `limit_snapshot`, and the no-login landing page lists them apart from failures (`not_judged`). Every other could-not-check stays queue-only. E2's hold half is not built (no holds exist). **Known wrong vs verify (rules table D2)**: `not_checked_kind` = `known_conflict` when a CONFIGURED limit's unit and the result's are of different KINDS (percent vs a count, MPN vs CFU, cells vs colonies, pH vs percent, count vs concentration -- `unitRefusalKind`), otherwise `verify` (`notCheckedKindOf`); never set on the printed-limit path. The review banner lists "Conflicts with your configuration" apart from "Could not confirm -- verify by hand"; nothing is judged or held, and the register does not carry the kind yet. **Bands (rules table D3, migration 0120)**: `spec_tests.category` (`indicator` / `compositional` / `zero_tolerance` / `regulatory_ceiling`, NULL = no band) gives an out-of-spec or could-not-check result a band via the pure `shared/specBand.ts`, attached AFTER judging by `attachSpecBands` in `specResultsWithConfig`: indicator review / >10x violation; compositional light / look / urgent; zero-tolerance top priority; regulatory ceiling note / call / violation around the configured legal ceiling (`regulatory_ceiling_value/_unit/_source`, `regulatory_band_factor` default 3x; aflatoxin M1 0.5 ppb is a code default in `KNOWN_REGULATORY_CEILINGS`, never written to the DB). A band orders (after verdict and criticality) and words the alert; it never changes a verdict, routes, or holds. Preview what a limit would catch with `bin/recheck-spec-limits --tenant <id>`. **The alias gap is on the page, not only in that script** — a limit whose analyte never matches what a supplier prints never runs, and the register cannot report a check that never happened, so `GET /api/spec-unmatched` lists every printed test name no analyte recognises with what it costs (prod Cush Co: 144 names, 2,074 results over 522 approved documents). One derivation, `shared/unmatchedAnalytes.ts`, shared with the CLI; the engine returns `unmatched_results` per result and `spec_test_id` separates an ALIAS gap from a missing-limit SCOPE gap. Spellings fold on the match key (`normalizeTestName`), so `Flavor`/`FLAVOR` is one row. Three answers per row: add as an alias (`POST /api/spec-tests/:id/aliases`, which MERGES — the PUT replaces the array and would delete a concurrent addition), create the analyte pre-filled with every spelling, or dismiss it as not a test (migration 0114, audited and undoable). The scan is capped at the 2,000 most recent documents and reports `scan_truncated`. **`version` moves only when the threshold does** (operator / value_min / value_max / unit) — one rule, `limitThresholdChanged`, shared by the REST PUT and `bin/lib/specLimitsImport.js`, which disagreed; notes, severity, criticality, active and a scope move do not bump, and `limit_snapshot` now actually freezes the `version` migration 0085 always claimed it did. The importer also takes an optional criticality column (the tier words the UI shows or the stored ones; blank = the default, an unknown word fails the row). **Criticality (migration 0095)** ranks each limit — stored `high`/`medium`/`low`, default `medium`, vocabulary owned solely by `shared/specCriticality.ts`; since rules table B1 (2026-09-27) it DISPLAYS as Critical / Major / Minor with a hover explainer on every chip (`SPEC_CRITICALITY_HELP`, draft copy held for AJ's wording; the critical tooltip says holds are not enforced yet, because they are not). Stored values are unchanged so frozen snapshots keep their meaning; the importer still accepts the former labels. It orders and colours the admin list, the review-queue banner/chip/row markers and the alert email, and is frozen into the snapshot; it changes no verdict and hides no result. **A watch records WHY (no migration -- 0084's `notes`, surfaced at last)**: AJ Conner, reviewing v2.7.0-v2.20.0, "tightening past what a supplier certifies against is a decision purchasing and the supplier will ask about, and it is hard to defend a year later with no recorded rationale." The column has existed since 0084 and the API has always accepted and returned it; NOTHING in the app ever read it, so nine limits on the live tenant carried a note nobody could see -- two of them open questions addressed to a person ("PRESENCE TEST -- confirm with Chris how the portal evaluates this"). Now the limit dialog ASKS for it whenever a supplier is chosen, in one box beside the review-by ("why, and when to look again" is one question in two halves), and Save is blocked without it; the same box on Supplier > Spec watch requires a reason for a required analyte (0109's `reason`). Not required tenant-wide -- the company standard does not justify itself to itself -- and **not enforced by the API**: `bin/lib/specLimitsImport.js` (which already writes the workbook's notes column) and `bin/seed-supplier-watch` would fail a whole import on one blank cell, and a limit that does not get written is worse than one whose reason is pending. Instead a supplier-scoped limit with no reason SAYS SO on both screens, because "no reason recorded" is itself the finding. **Frozen into `limit_snapshot` as `rationale`, SUPPLIER-SCOPED ONLY**: a note is editable and the question a year from now is what it said when the result was judged, which is the review-by's own argument -- but a tenant-wide note is commentary about the company standard and copying it onto every verdict would fill the register with prose no register row is asked. Both sides of an edit are in `spec_limit.updated`, and `spec_limit.created` carries the reason, because the audit row is the only copy nobody can rewrite. Editing a rationale does NOT bump `version`: it is not a threshold. **Unit equivalence (migration 0093)** is the one per-tenant setting that changes a verdict: off by default, it lets CFU/mL be judged against a CFU/g limit for fluid tenants, names itself in every reason it produces, and is set on Settings › Spec Limits. **Unit classes (`normalizeUnit` / `resolveUnits`)**: exact arithmetic is automated and carries `conversion` even at 1:1 (`sample_basis`, or `unit_arithmetic` for ppm = mg/kg = µg/g, ppb = µg/kg, mg/100g = 10 ppm, 1% = 10,000 ppm, mg/L within its own mass-per-volume class); product-dependent pairs refuse with a reason from the rule (mass fraction vs mg/L, % v/v vs weight). Never compared: CFU vs MPN, `cells/mL` (its own kind) vs CFU, log CFU vs linear, a bare `oz` vs g or mL ("fl oz" = 29.5735 mL and "oz wt" = 28.3495 g are). A method-less count ("per ml.", "/g") is recognised but NOT assumed to be CFU: on prod every such row is Andersen's regulatory threshold lifted into the results, and assuming CFU made two false out-of-spec alerts. **Yeast & mold**: a combined result is never judged against a separate Yeast/Mold limit (it can't be split), and separate results are never summed against a combined limit; both are `not_checked` with the reason (`yeastMoldMismatch`, checked on the analyte's NAME so a misplaced alias cannot defeat it). Closed-vocabulary spelling variants ("Yeasts & Moulds") match a test of the same combination.

### Supplier Requirements from Real Data (migration 0112)

### Request Composer

- **Request Composer**: Compose a document request against one supplier, issue it, and amend it without destroying what was originally sent (migration 0090). A line SHOULD resolve to a `requirement_id` so the arriving document is a registry object the gap engine can count; free text is supported as an escape hatch but must be declared (`line_kind: "free_text"`) and is counted separately on every response. Per-line status is the client's five: `not_started | received | under_review | accepted | needs_attention`, with no transition graph imposed. Amendments after issue create a NEW version (`root_request_id` + `version`, previous row stamped `superseded_at` and otherwise frozen); re-issue starts a new root for renewals and new items under an approved vendor. One issue path (`issueRequest` in `functions/lib/document-requests.ts`) writes one internal `request_routing` row and one audit row regardless of what filled the draft — a future generator drafts, a human issues. The external projection is an allow-list (`buildSupplierRequestView`), same discipline as `buildAlertLandingView`. `closure` stays read-only: a typed line surfaces the confirmed `document_requirements` links from that supplier and does not move `status`. **Arrivals (migration 0104)**: what a supplier sends through their link is reviewed at `/requests/arrivals` (and "What came back" on each request) via `/api/request-uploads`. A person decides per claim (`request_upload_lines`): **accept requires the file to be approved in the Review Queue first** (409 otherwise). Queue approval judges the extraction, accept judges "satisfies what we asked", and the two stay separate judgements. **They can be ONE action**: for a `request_link` item the Review Queue card offers the claims pre-ticked plus an explicit accept / send back / decide later choice (Approve waits for it), sent as `arrival_decision` on PUT /api/queue/:id (reject + send back too). Doc-independent checks run before the approval; if the decide half still fails afterwards the response is 200 with `arrival_decision.applied: false`, the approval stands and the arrival stays pending. Audit rows carry `via: 'review_queue_combined'`. Accept names the document on `request_lines.accepted_document_id` and confirms the registry link (`source='request_accept'`), and it never overrides a human `rejected` link. Needs-attention works at any stage, and the supplier reads `attention_reason`, never `status_note`. Claims map onto the current version by line identity. Logic: `functions/lib/request-arrivals.ts`.
