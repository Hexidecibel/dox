## Names that stay put, packs that can be updated

Two things that used to drift now hold still. The internal name the portal
keeps for a document type, a requirement or a claim type (its slug) is fixed
the day the item is created, so renaming it no longer breaks whatever was
pointing at it. And a starter pack, which could be applied once and never
updated, now carries a version: an organisation can see which version it is
on and preview what an update would change before anything is written.

No pack content changed in this release. Both packs are at version 1, so
there is nothing to update to yet; this release is the machinery. It was
checked by automated tests and two rounds of independent review; nobody has
yet clicked through the new Settings > Starter pack screen, or the new
duplicate notices, in a browser.

### If you were set up before this release, read this

- [existing] **Your organisation has no record of what its starter pack wrote, and until it has one, Apply and Update refuse it.** The portal only began keeping that record with this release. Without it, an update could not tell an item you removed on purpose from one the pack added later, and would put both back. So rather than guess, applying a pack again and updating a pack both answer "not recorded yet" for an organisation set up earlier. Recording it is a one-time operator step per organisation, being done after this release is live. It reads your document types, requirements, claims and limits and notes which match the pack, which differ and which are absent. It changes none of them. Nothing else in the portal is affected while you wait.

### Changed

- [existing] **Renaming a document type no longer changes its slug.** It used to be worked out again from the new name on every rename, so a renamed type stopped being the one a saved link, a pack or the setup wizard was looking for. A slug is now set once, when a document type, requirement or claim type is created, and never changes. A request that tries to change one is refused and says why. A renamed type is still found in search by its new name and by its old one.
- [existing] **Creating something you already have is refused, and the refusal names what you have.** When you create or rename a document type, requirement or claim type, the name is compared with everything of that kind your organisation holds, switched off or not, and with the items of your starter pack, including the other names the pack lists for them ("Spec Sheet" for "Specification Sheet", "COA", "SDS" and "MSDS"). Names are the same when they match letter for letter after ignoring capitals, spaces and punctuation; nothing looser, so "Kosher Certificate" is never mistaken for "Halal Certificate". If the existing one is switched off, the notice says so, and the answer is to switch it back on.
- [existing] **An admin can override that refusal, and the override is recorded.** The notice offers the real choices: create it as the pack's item, create a separate one anyway, or go back. Creating a separate one anyway is written to the audit log with the item it duplicates.
- [existing] **Applying a pack no longer depends on your organisation's own slug.** A pack used to find its rows through an id built from the organisation's slug. If that slug had been changed, or somebody had already created a row by hand under one of the pack's slugs, the whole apply failed, or the setup wizard reported every line of a requirements packet as unknown. A pack now finds a row by its own slug inside your organisation, and a hand-made row that holds a pack slug is adopted as it stands. It is not duplicated, and nothing on it is overwritten.
- [existing] **Applying a pack only ever adds.** It never changes a row you already have, and it no longer puts back a link you deleted. A newer version of a pack never arrives through Apply; it arrives only through the update preview below.

### Added

- [config] **Starter packs carry a version, and Settings > Starter pack shows the one you are on.** When a newer version exists, an admin can preview the update. Nothing is written by looking. A changed pack default still reaches a new organisation at setup; it reaches an existing one only when an admin previews and applies the update.
- [config] **The preview says what would happen to each item, in five groups.** Items you have not touched are updated. Items you changed are kept as they are, shown with what the pack wrote, what you have now and what the pack now says, and they change only if a person ticks them. Items new to the pack are added, unless you already have the same thing under another name, in which case a person decides. Items the pack no longer has are flagged and left exactly as they are; an update never deletes or switches anything off. Items you deleted stay gone unless a person ticks them.
- [config] **An update never loosens a rule.** A change that would let a document type be sent more freely is reported, not made, even when ticked; a person makes it on Document Types. A tighter rule is applied and audited as if an admin had set it. A limit whose threshold moves is recorded as a new version of that limit, with before and after in the audit log. No past judgement and no past renewal decision is rewritten.
- [config] **A real update needs a signed-in admin and the preview it was clicked from.** An API key can preview and cannot apply. If anything changed between the preview and the click, nothing is written and the screen asks for a fresh preview. A pack rename that would land on a name another of your items already has is held and listed, never applied. A pack version never goes backwards.
